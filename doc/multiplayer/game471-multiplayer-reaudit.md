# game471 Multiplayer Correction Audit

**Audit date:** 2026-09-02
**Binary database:** `H:\gc\game471.exe.i64`

This audit rechecks the multiplayer redesign after live one-player testing
proved that the native client sends `action = 0`. It deliberately separates
five kinds of evidence: native emission, native receive requirements, live
observation, pre-redesign repository behavior, and current server
policy/inference.

## Outcome

Two real MainServer compatibility regressions were introduced during the
redesign:

1. Selector `1902` / card request `8961` was assigned entry-dependent actions
   `1` and `2`. The native class initializes the action source to zero, never
   changes it, and live requests carry zero.
2. The nine ordinal result fields in card request `8709` were shortened from
   `_1st`/`_2nd`/`_3rd` to `_1`/`_2`/`_3`. Native serializers emit the ordinal
   names, and the pre-redesign model already had them.

Both are corrected in the current implementation and protected at XML,
handler, and service boundaries. The channel-6 relay re-audit found a different
kind of problem: its strict rules match normal game471 emissions, but several
were documented as native receive requirements or official-relay facts. They
are now classified accurately as emission allowlisting, hardening, or
reconstructed policy.

## What was already known before the redesign

The user's concern was correct. The pre-redesign repository contained:

- `GC-local-server-rewrite/models/OnlineMatchingResultData.cs`, whose nine
  ChoETL mappings used the exact ordinal names;
- `GC-local-server-rewrite/models/OnlineMatchingUpdateData.cs`, which included
  `action`, `event_id`, `matching_id`, and `message_id`.

Those definitions did not mean the old handlers consumed everything. The old
8961 handler deserialized a different entry DTO and ignored action semantics;
the old 8709 handler returned status `1` without parsing the result-data model.
Nevertheless, the correct schemas were existing evidence and should have been
preserved. Commit `2e76ff4` introduced both shortened result tags and the
unsupported action-role interpretation.

independently reconstructs transient channel-6 membership from the shared
`matching_id`, machine ID, entry number, and profile-bearing packets.

## 8961 action and timeout control

`OnlineMatchingXml_WriteUpdateRequest_8961` reads four values from its request
object and writes `action`, `event_id`, `matching_id`, and `message_id`.
`CNesysOnlineMatching_Construct` initializes the action source at object offset
`+0x90` to zero. The audited class has no later writer to that field.

The static result is independently supported by the latest MainServer request
log: one cabinet sent 18 consecutive 8961 polls with `action = 0` at roughly
ten-second intervals.

The client worker's actual matching controls are:

- `matching_wait_time * 1000` schedules the next 8961 request;
- immediately before that request the client reannounces its `A6` profile;
- `status = 3` exits HTTP matching;
- `matching_remaining_time` is copied response/UI data, not the worker's local
  deadline;
- there is no fixed local HTTP-matching timeout.

Consequently, a server that never returns status `3` can keep one client
waiting indefinitely. The current MainServer policy resolves a one-player room
at the elapsed 99-second search deadline and returns status `3` on the first
poll at or after that deadline. If a second player joins first, MainServer
replaces the search deadline with a 40-second formation deadline. Those
`99`/`40` values are configurable policy informed by UI/video observation, not
constants recovered from the client binary.

## Verification boundary

Automated tests can prove exact XML deserialization, action validation,
elapsed-time room transitions, byte codec behavior, and pure relay routing.
Static IDA evidence can prove native client emission and receive behavior. They
cannot prove retired official-service timing or relay policy, and they do not
replace a corrected-build cabinet run. Remaining external acceptance is an
official packet capture where available plus two-, three-, and four-cabinet
sessions covering matching, gameplay, result upload, leave, loss, and expiry.
